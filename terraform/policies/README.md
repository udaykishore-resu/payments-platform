# `terraform/policies/`

IAM policy documents that are either (a) consumed by a stack via `templatefile()`,
or (b) applied outside this repository and kept here so the estate's authorization
model is reviewable in one place.

| File | Applied by | Notes |
|---|---|---|
| `irsa-permissions-boundary.json.tftpl` | `envs/*/main.tf` → `module.eks.permissions_boundary_arn` | Rendered with `templatefile()`, attached to every IRSA role and to the node role. |
| `terraform-deploy-role.json.tftpl` | The bootstrap stack (see `terraform/README.md` §1) | What the CI deploy role may do. Not applied by the env stacks — a role cannot be the thing that grants itself its own permissions. |
| `break-glass-session-policy.json` | The IdP, as a session policy at `AssumeRole` time | Caps a break-glass session regardless of what the role's own policy says. |
| `scp-payment-platform-ou.json` | `pp-org-management`, at the OU level | **Not applied by this repository.** Reproduced here so a reviewer can see the outer boundary the env stacks operate inside. Applying an SCP from an account inside the OU is impossible by design. |
| `reference/*.json` | Nothing | Rendered copies of the per-deployable IRSA policies, regenerated by `make policies` from `terraform show -json`. They exist so `checkov`, `conftest` and the QSA's evidence pack can read a policy without running a plan. Editing one has no effect — the source of truth is `modules/eks/irsa.tf`. |

## Why the per-deployable policies are HCL, not JSON

`aws_iam_policy_document` is type-checked at plan time: a malformed condition
operator, an unknown ARN interpolation or a missing `resources` argument fails
the plan. A raw JSON file fails at `aws iam create-policy` time, or — worse —
succeeds and grants nothing, because IAM silently accepts a policy whose
conditions never match.

The reference JSON under `reference/` closes the gap for tooling that cannot run
Terraform, and CI asserts the two are in sync.
